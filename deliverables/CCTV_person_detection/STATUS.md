# 사람 인식 구현 및 검증 상태

## 확인된 결과와 남은 문제

현재는 사진 사람 검출이 성공하고, 실시간 카메라 입력에서 NPU 실행 오류가 재현되는 상태다. 실시간 사람 인식 완료본이나 전체 SRS 충족본은 아니다.

| 시험 | 관측 결과 | 해석 범위 |
|---|---|---|
| BGR 사진 추론 | 23~24개 검출, detect_ms 97.8~105.5ms | 단일 사진의 전처리·추론·후처리 성공. 실시간 인식률이나 지속 처리 FPS는 미검증 |
| 통합 프로그램 카메라 입력 | rknn_run -1, task counter 22 또는 10 등에서 실패 | 실시간 추론 미해결. 실패 위치는 고정되지 않음 |
| AI 실패 후 영상 경로 | VIDEO fps=15.0 ai=disabled 반복 | 인코더 결과 회수 지속 확인. VLC 실제 수신·장시간 재생을 이 로그만으로 보장하지 않음 |
| 카메라 시험 종료 후 사진 재실행 | 재부팅 없이 23개, 98.2ms 성공 | 실패 후 NPU가 반드시 계속 사용 불능이 되는 것은 아님 |
| 기존 스트리머 병행 비교 요청 후 사진 실행 | 24개, 97.8ms 성공 | 제공 사진 로그에는 스트리머 동시 가동 증거가 없어 병행 성공 해석은 실행 조건 확인이 전제 |
| 고정 사진 + 카메라/송출 (-P) | ARM 빌드 성공, 보드에서 task counter 19 timeout | 카메라 픽셀 변환을 우회해도 실패 |
| 고정 사진 + AI VI만 (-S -P) | task counter 19 timeout | 주 VI·인코더·RTSP 없이도 재현 |
| 카메라 미초기화 + 작업 스레드 (-N -P) | 최소 12회 성공 후 task 97 timeout | 카메라 동시 활성 없이 반복 중 실패 |
| 위 실패 직후 별도 사진 | 재부팅 없이 23개/97.8ms 성공 | 실패 후 항상 사용 불능이 되지는 않음 |
| 카메라 미초기화 + 주 스레드 (-N -M -P) | 새 비교 옵션 구현 | ARM 빌드·보드 시험 대기 |

현재 BGR 결과의 23~24개 차이를 정확도 개선으로 해석하지 않는다. 24개 결과의 마지막 점수는 0.510으로 임계값 0.5에 가깝다. 검출 개수만으로 누락·중복 여부를 판정할 수 없다.

## 로그를 읽는 기준

```text
VIDEO fps=14.8 ai=enabled
E RKNN: failed to submit! ...
NPU DISABLED: rknn_run: -1; video loop remains independent (no automatic retry)
VIDEO fps=15.0 ai=disabled
```

`ai=enabled`는 AI 처리가 활성화되어 있다는 뜻이며 첫 추론의 완료를 기다릴 때도 표시된다. 추론 성공은 `PERSON count=...`로 확인한다. `ai=disabled`는 오류 후 추가 추론을 중단한 상태다. 위 흐름을 인식 성공 후 중단으로 해석하면 안 된다.

`VIDEO fps`는 인코더 결과 회수율이다. 설정 FPS, 센서 FPS 또는 VLC 종단 지연과 같지 않다. `-f 5`는 AI 입력 선택 상한이며 영상 5fps 설정이 아니다. `detect_ms`는 전처리·추론·후처리를 포함한다.

## 원인 조사 범위

커널 로그에는 약 6초 작업 대기 후 timeout과 soft reset이 기록된다. 임시 진단 모듈에서는 약 1초부터 5초까지 task counter가 동일하게 유지되는 구간도 관측했다. 단순히 처리 속도가 느린 것인지의 문제를 넘어 작업 진행이 정체되는 단서지만, 특정 드라이버·하드웨어·코드를 원인으로 확정하지는 못했다.

송출과 추론을 분리한 설계 및 AI 오류 격리는 로그로 일부 검증되었다. 버퍼 복사, 색상 변환, 초기화 순서, 스레드 사용, 보조 VI 활성화와 공유 자원의 적합성까지 검증되었다는 뜻은 아니다. 프로젝트 코드도 원인 후보에 포함한다. NPU 사용률 99~100% 표시만으로 정상 연산 중인지 과부하인지 판단하지 않는다.

## 다음 비교 시험

새 -N -M -P 모드로 같은 모델·입출력 버퍼를 재사용하면서 주 스레드에서 반복 추론한다. 같은 새 바이너리의 -M 없는 작업 스레드 모드와 비교한다. 기존 -N은 정상 기준 직후에도 일부 성공 후 실패했으므로 카메라 동시 활성 또는 이전 오류 잔류만으로 전체 현상을 설명할 수 없다. 단발 사진 성공을 근거로 작업 스레드가 원인이라고 확정하지 않는다. 상세 절차는 THREAD_REPEAT_TEST.md에 있다.

## 검증 한계

사용자가 -P 소스를 ARM 빌드하여 -P 및 -S -P를 보드에서 실행한 결과와, 새 -M 소스의 검증 상태를 구분한다. 기존 호스트 후처리/최신 프레임 슬롯 검사는 전체 카메라·NPU 검증이 아니다. 새 -M 패키지는 공통 추론 제어 코드의 모의 모델 호스트 검사와 ZIP 무결성을 확인했으며 전체 ARM 빌드와 보드 검증이 필요하다.

영상 박스 표시, 이중 스트림, 이벤트 녹화, 프라이버시 존, 자동 복구 등 전체 SRS 기능은 이 전달본의 완료 범위가 아니다. 이번 자료는 사람 검출과 연관된 스트리밍 코드 및 조사 결과에 한정한다. 보드 실행은 사용자가 수행하며 자동 전송·드라이버 교체 기능은 제공하지 않는다.
