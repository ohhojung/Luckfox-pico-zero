# 2026-11-15 heartbeat 계약 우선 적용

사용자 요청으로 서버 JSON의 rtsp_ok는 팀장님처럼 영상 프로세스 실행 여부로 통일했다. 우리 영상 프로세스는 cctv-dual-rtsp, VPN은 wg0이다. wg_ok는 IFF_UP, config_version은0, status는online, MAC은대문자12자리다. 최근 프레임 검사는 S59cctv health로 별도 수행하며 heartbeat JSON에 추가 필드를 보내지 않는다. 아래 프레임 건강도를 heartbeat에 적용한다는 내용은 이전 제안이며 취소됐다.

# 안정성 보완 판단 — 2026-11-14

## 선택한 구조

우리 모듈형 cctv-dual-rtsp와 heartbeat를 유지한다. 팀장님 rkipc 운영 기록은 검증 근거로 참고하되 해당 보드 전용 설정을 복사하지 않는다.
사용자 보드에서 H265/VTS3750/양쪽 약18fps 및 재부팅 자동 실행을 확인했다. 이 기록은 장시간 안정성이나 서버 HTTP200 검증을 뜻하지 않는다.

## 이번 보완

1. 기본 cctv-dual-rtsp의 heartbeat rtsp_ok는 살아 있는 프로세스와 일치하는 PID의 상태 파일을 확인한다. state=running, 양쪽 양수 프레임 수, 상태/마지막 프레임 나이 5초 이내를 모두 요구한다. 누락·중복 키·잘못된 수치·미래 시각은 false.
2. 사용자가 별도 --rtsp-process를 지정하면 기존 프로세스 존재 기준을 유지한다. 기본 배포 대상만 새 상태 형식을 요구한다.
3. 잘못된 옵션(-F 184 등)은 프로세스 락·카메라 초기화·재시도 전에 즉시 실패한다.
4. 기존 rkipc 점유 감지와 cctv 프로세스 락을 유지한다. 다른 프로그램을 무조건 kill하지 않는다.

JSON 필드와 서버 URL은 바뀌지 않지만 rtsp_ok의 판정이 강화됐다. 이는 서버에서 정상으로 표시되는 조건이 달라지는 의도된 변경이다.
wg_ok는 기존 IFF_UP 의미를 유지한다. 핸드셰이크/서버 수신 확인은 별도다.
rtsp_ok=true도 영상 내용의 움직임, 네트워크 수신, 웹 재생을 보장하지 않는다. 반복 정지 화상 인코딩은 별도 원본/PTS 비교가 필요하다.

새 streamer와 heartbeat가 포함된다. 보드에는 아직 배포하지 않았다.
기존 정상 서비스 파일을 백업한 후 두 바이너리를 교체하고 각각 재시작해야 한다. 전체 install.sh는 이미 설치된 보드의 자동 업그레이드 용도가 아니다.
기본 H265/18fps/VTS3750과 S59cctv 설정은 유지한다.
서버가 실제 rtsp_ok=false/true를 어떻게 표시하는지는 통합 검증이 필요하다.
