# CCTV 동작 문제 재검토

## 판단 요약

사진 추론은 약 100ms에 성공하지만 카메라가 활성화된 일부 조건에서는 NPU 작업이 약 6초 뒤 timeout으로 끝난다. 가장 우선할 조사 영역은 **현재 펌웨어·카메라 설정에서 ISP와 NPU를 함께 사용하는 경로**다. 드라이버, 메모리 접근, 공유 자원 및 프로그램 사용 방식 중 정확한 원인은 아직 확정되지 않았다.

초기의 CMA 메모리 할당 실패, 최근의 NPU 실행 timeout, 영상의 20/30fps 불일치는 서로 구분해야 한다. 세 현상을 모두 단순한 보드 성능 부족으로 설명할 근거는 없다.

## 보드·카메라 사양과 실제 구성

|---|---|---|

| ISP·인코더 | 공식 제품 ISP 8M@15fps, 인코더 5M@30fps; 위키 ISP 5M@30fps | 입력 해상도와 처리 구간을 붙여 읽어야 함 |

| NPU 입력 | YOLOv5 RKNN640×640, BGR letterbox, INT8 출력 | AI VI640×360을 모델 크기로 재가공 |
| 실행 환경 | Linux5.10.160 / RKNN runtime1.6.0 / driver0.9.2 / AIQ5.0 | 버전 조합에 따른 문제 가능성은 별도 검증 필요 |

공식 보드 사양은 [Luckfox 위키](https://wiki.luckfox.com/Luckfox-Pico-Zero/) 및 [제품 페이지](https://www.luckfox.com/luckfox-pico-zero)를 확인했다. [Rockchip RV1106 데이터시트 Rev1.7, p.11](https://files.luckfox.com/wiki/Luckfox-Pico/PDF/Rockchip%20RV1106%20Datasheet%20V1.7-20231218.pdf)은 G3 최대 입력 조건을3840×2160@15fps로 명시한다. 과거20fps 관측을 무효화하거나 모든 설정에서15fps가 절대 상한이라고 해석하지 않는다.

센서 수치는 [Sony IMX415-AAQR 자료](https://www.sony-semicon.com/files/62/flyer_security/IMX415-AAQR_Flyer.pdf) 기준이다. 사용자의 IMX415 모듈 세부 렌즈·세부 suffix를 새로 확인한 것은 아니므로 특정 렌즈 화각을 사용자 장비의 확정 사양으로 추가하지 않았다. [Luckfox IMX415 문서](https://wiki.luckfox.com/IMX415-Camera/)도 모듈별 렌즈 사양을 구분한다.

## 시험에서 확인한 사실

| 시험 | 관측 | 결론의 범위 |
|---|---|---|
| 초기 모델 출력 검사 | 논리 크기와 할당 크기가 달라 앱이 거부 | 검사 수정 후 추론까지 진행. 현재 실행 timeout과 다른 문제 |
| rkipc와 사진 추론 | CMA409600byte 할당 실패, errno12 | 연속 메모리 부족 경로의 실제 실패 확인 |
| 사진 단독 | BGR23~24개,97.8~105.5ms | 모델·실행 코드가 항상 실패하는 것은 아님 |
| 통합 카메라+NPU | 할당 완료 뒤 rknn_run 실패 | 실행 중 작업 완료 실패이며 초기 할당 오류와 구별 |
| -S 단일AI VI | VENC/RTSP/주VI 없이도 실패 | RTSP·H.265·두VI는 모든 실패의 필수 조건이 아님 |
| 제조사640×360 스트리머+별도 사진 | CMA사용75480/102400KiB에서 실행 timeout | 우리 실시간 프레임 변환 코드만으로 전체 이력을 설명하기 어려움 |
| 카메라 가동 후 정지, 보유 NPU컨텍스트 재개 | 과거 gdb 통제 시험에서 사진 성공 | 카메라 초기화가 항상 NPU 메모리를 영구 파괴하는 것은 아님 |
| 현재 원본 모듈에서 카메라 두 번 실패 뒤 사진 | 재부팅 없이23개/98.2ms 성공 | 실패가 항상 재부팅까지 지속되는 것은 아님 |
| 최근 기존 스트리머 병행 요청 후 사진 | 24개/97.8ms 성공 | 첨부에 스트리머 동시 상태가 없고 반복 횟수도 부족. 동시 실행 항상 성공으로 확대하지 않음 |
| 센서1944×1097/12bit | 모드 적용은 됐으나 AIQ 통계 스레드 SIGSEGV | 센서 축소로 NPU 해결 또는 미해결이라고 판정할 수 없음 |
| NPU420MHz 비교 | 사용자가 동일 증상 보고 | 당시 런타임 주파수 원본 로그는 부족. 무조건 재시험을 반복하지 않음 |
| 오류 후 인코더 | VIDEO약15fps 유지 | 송출과 AI 오류 격리 일부 검증. VLC 수신·장시간 안정성 증명은 아님 |
| 고정사진 -P | ARM빌드 성공, 사진612×368 적용 후 task19에서 약6.34초timeout | 카메라 픽셀변환을 우회해도 실패. 오류 후 VIDEO15fps 유지 |
| 고정사진 -S -P | 주VI/VENC/RTSP없이 AI VI1만 활성, 새job task19/약6.56초timeout | 카메라픽셀변환과송출경로를모두제외해도재현. ISP/센서/VI와NPU동시사용및앱공통경로는남음 |

과거 RGB 사진과 현재 BGR 사진의 검출 수를 정확도 향상/저하로 단정하지 않는다. 모델 파일명·해시가 같더라도 전처리 및 프로그램 버전이 다른 실험은 따로 취급한다.

## 원인 후보 우선순위

### 1. ISP 활성 상태에서 NPU 작업이 정체되는 문제 — 가장 우선할 영역

사진은 성공하고 카메라 활성 조건에서 실패하는 반복 관측이 있다. RTSP 없이도, 별도 프로그램으로도 실패했다. 진행 진단에서는 약1~5초 샘플 사이 task22 또는95가 고정됐고 약6초 뒤 timeout/soft reset이 나타났다. 단순히 인식이 늦는 현상보다 작업 진행 정체에 부합한다.

이것만으로 AXI 버스 경합, IRQ 전달 결함, 런타임·드라이버 버그 중 하나를 확정할 수 없다. raw0xc0000의 의미도 제공 헤더만으로 확정하지 않았다. 드라이버의 부하 계산은 미완료job 시간을 포함하므로99~100%를 정상 연산 포화나 전원 차단 증거로 사용하지 않는다.

동일 보드·센서의 [Luckfox 이슈359](https://github.com/LuckfoxTECH/luckfox-pico/issues/359)와 [Rockchip 이슈544](https://github.com/airockchip/rknn-toolkit2/issues/544)에도 유사 증상이 보고됐다. 같은 작성자의 중복 보고다. 작성자의 AXI 경합 설명은 가설이며 제조사 확정 원인이나 해결책으로 취급하지 않는다. 외부 보고는 online1, 우리 주요 로그는 online0/multiISP1이라는 차이도 있다.

### 2. 4K 입력과 ISP unite/readback 경로 — 성능·동시성 부담 후보

출력을1080p나540p로 줄여도 센서 입력3864×2192가 유지됐던 시험이 있다. 3840×2160은1920×1080보다 픽셀 수가4배다. 이는 입력 처리량 차이를 보여줄 뿐 실제 메모리 트래픽이 정확히4배라는 뜻은 아니다.

FPS 진단에서는 센서/CIF약30fps, ISP/VI약20fps가 관측됐고 VENC 없는 VI 단독에서도 약20fps였다. 따라서 해당 시험의 제한 구간은 클라이언트 디코딩이나 Wi-Fi보다 ISP/VI 쪽에 가깝다. 최근 NPU앱의 약15fps는 VTS4500 등 조건이 달라 같은 시험으로 묶지 않는다.

`over virtual isp max resolution, force to 2 readback` 경고는 조사한 소스에서 ISP_UNITE_ONE 조건으로도 출력된다. 경고 문구만으로 해상도 초과나 메모리 대역폭 고갈을 증명하지 못한다. 작은 센서 모드 시험은 AIQ 충돌부터 분리해야 한다.

### 3. 우리 코드의 버퍼·스레드·초기화 사용 방식 — 배제하지 않은 후보

현재 코드에는 카메라 버퍼를 독립 BGR로 복사하고, 슬롯에서 소유권을 전달하며, NPU를 하나의 추론 스레드에서 호출하는 구조가 있다. 검토 범위에서 반환된 카메라 포인터를 그대로 NPU에 넘기거나 같은RKNN컨텍스트에 동시추론하는 명백한 흐름은 찾지 못했다.

그러나 실제DMA/캐시 동기화 계약, 라이브러리의 스레드 사용 제약 및 런타임 상호작용까지 검증한 것은 아니다. 사진은 같은 스레드에서open/infer, 통합은 주스레드open 후 다른스레드infer라는 차이가 있다. 이것 자체가 잘못이라는 증거도 없다.

공식 코드 역시 모델을 ISP/SYS보다 먼저 초기화하고 create_mem/set_io_mem/rknn_run을 쓴다. 그 순서나 명시적 mem_sync 부재만으로 우리 코드 결함을 단정하지 않는다. 현재 -P 비교로 입력 경로를 먼저 분리하고 나머지는 한 번에 하나씩 변경해야 한다.

### 4. 카메라 모드·IQ·AIQ·드라이버 조합 — 구체적 호환성 검증 필요

작은12bit모드의 librkaiq 통계스레드 충돌은 조합별로 문제 가능성이 있다는 관측이다. IQ파일이 센서 이름에 맞게 로드된다고 모든 센서모드에서 동작을 보장하는 것은 아니다. 현재 모델이 사진에서 작동하므로 모델/런타임의 완전한 비호환은 덜 설득력 있지만 동시 실행 문제를 배제하지 못한다.

[공식 YOLO 예제 지원표](https://github.com/LuckfoxTECH/luckfox_pico_rkmpi_example/tree/kernel-5.10.160)는 RV1106/Buildroot/SC3336이다. 공식 코드 참고를 Zero+IMX415 구성의 정상 동작 인증으로 확대하면 안 된다. 버전을 무작정 올리기보다 일치하는 전체 조합으로 대조해야 한다.

### 5. CMA 부족·발열·전원·네트워크 — 현상별로 판단

CMA 부족은 초기 오류에서 확인된 원인이다. 반면 최근 timeout 시험에는 입출력 할당이 완료됐고 CMA사용74712/102400KiB인 샘플도 있었다. 용량 여유가 있어도 단편화·순간피크·메모리 접근 문제까지 없어지는 것은 아니지만 모든 timeout을 단순 RAM부족으로 분류할 수는 없다.

온도46.4~52.3°C 구간에서도 실패했다. 과거70.7°C나 카메라 뒷면 발열만으로 현재 timeout을 열 때문이라고 단정하지 않는다. 전원 측정은 없어 전원 문제도 미확정이다. Wi-Fi/VLC는 수신 끊김과 지연의 후보지만 로컬사진 프로그램 및 VENC/RTSP없는 시험의 NPU오류를 직접 설명하지 못한다.

## 다음에 확인할 순서

1. -P와-S -P 고정사진 비교가 모두 실패했다. 다음은 동일한 모델초기화·추론스레드·프레임슬롯을 유지하되 카메라/ISP/VI를 시작하지 않는 고정사진 대조를 준비한다. 기존 사진프로그램은 동일스레드에서초기화·추론하므로 이 차이가 남는다. 해당 전용옵션은 아직 구현 전이다.
2. 별도 스트리머+사진 시험은 스트리머 명령·실행 중 상태·사진 결과를 함께 기록해 최근 성공과 과거 실패의 조건을 맞춘다. 초기 할당 오류와 실행timeout도 구분한다.
3. -P가 성공하면 저장한 실제 카메라 프레임을 카메라 종료 상태에서도 추론해 입력·변환 문제를 더 분리한다. -P도 실패하면 기존 -S 실패 근거를 활용해 프로그램 분리/동일스레드RKNN사용 등 최소 변경을 차례로 비교한다.
4. 저해상도 센서 경로는 호환 IQ/AIQ 조건을 확인한 뒤 별도로 조사한다. VI 출력 해상도만 낮춘 것을 센서 입력 축소로 취급하지 않는다.

지금 단계에서 timeout 시간만 늘리거나, IRQ완료를 강제 인정하거나, 클록/QoS/펌웨어를 동시에 바꾸면 원인 분리가 어려워진다. 이번 재검토에서는 소스·공식자료만 읽었으며 보드/VM 실행과 설정 변경은 하지 않았다.
